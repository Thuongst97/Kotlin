Lesson 13 · Advanced Kotlin

Coroutines

Apps constantly wait — for the network, the disk, a timer. Coroutines let you write that waiting code as if it were simple sequential code, without blocking threads and without callback pyramids. On Android they're the standard way to do anything asynchronous.

⏱ 75 min🎯 Advanced📦 kotlinx-coroutines 1.10

  • Explain what suspend really means

13.1Why coroutines?

Android's main thread draws the UI. If it's blocked for more than a few milliseconds the app stutters; after ~5 seconds the system shows “App Not Responding”. So slow work (network, database) must happen elsewhere — and the result must come back to the main thread. Historically that meant threads + callbacks:

Callbacks
Coroutines

A coroutine is a suspendable computation. When it waits, it suspends: it saves its state and frees the thread to do other work. When the result arrives, it resumes — possibly on another thread. Coroutines are extremely cheap: you can run 100,000 of them where 100,000 threads would exhaust memory.

🎭
Analogy

A thread is a waiter; a coroutine is a table's order. A blocking waiter stands at the kitchen door until the dish is ready. A suspending waiter puts the order in, serves other tables, and comes back when the kitchen rings the bell. Same number of waiters, many more tables served.

📦
Setup

The suspend keyword is part of the language; the builders (launch, async…) come from the kotlinx-coroutines-core library. Android projects get it via androidx.lifecycle; in a plain Gradle project add implementation("org.jetbrains.kotlinx:kotlinx-coroutines-core:1.10.2"). The ▶ Run playground has it built in.

13.2suspend functions & runBlocking

A suspend function can pause without blocking its thread. It can only be called from another suspend function or from a coroutine builder. delay() is the suspending equivalent of Thread.sleep().

🔬
Under the hood

The compiler transforms every suspend function into a state machine and adds a hidden Continuation parameter — a callback that knows where to resume. You write sequential code; the compiler writes the callbacks. That's why calling a suspend function from regular code is a compile error: there's no continuation to pass.

13.3Builders: launch and async

launch { } → Job

Fire-and-forget: starts a coroutine that doesn't return a result. The Job lets you join() (wait) or cancel() it.

async { } → Deferred<T>

Starts a coroutine that computes a value. Call await() to get it (suspends until ready). Use it for parallel work.

Notice “launched, doing other work” prints before the first tick: launch schedules the coroutine, and it starts once the current one suspends (here at join()).

13.4Structured concurrency & scopes

Every coroutine runs in a CoroutineScope, and coroutines started inside another become its children. This tree gives three guarantees:

  1. A parent waits for all its children to finish.
  2. Cancelling a parent cancels all its children.
  3. If a child fails, the parent and its other children are cancelled and the error propagates up.

So no coroutine can leak: when the scope ends, everything in it is done. On Android, viewModelScope is cancelled when the ViewModel is cleared and lifecycleScope when the Activity/Fragment is destroyed — your work automatically stops when the screen goes away.

🚫
Avoid GlobalScope

GlobalScope.launch creates a coroutine with no parent: nobody cancels it, nobody waits for it, and its errors go nowhere useful. It breaks structured concurrency and leaks work. Use the scope of the component that owns the work.

13.5Dispatchers & withContext

A dispatcher decides which thread(s) a coroutine runs on.

DispatcherThreadsUse for
Dispatchers.MainAndroid UI threadUpdating UI, calling suspend functions that are main-safe. Default for viewModelScope/lifecycleScope.
Dispatchers.IOLarge shared pool (64+)Blocking I/O: files, legacy blocking network/database APIs.
Dispatchers.DefaultOne per CPU coreCPU-heavy work: sorting big lists, JSON parsing, image processing.
Dispatchers.UnconfinedWhatever thread resumes itRarely; special cases and tests.

withContext(dispatcher) { } switches to another dispatcher for a block and returns its result — then you're back on the original thread. The golden rule on Android: suspend functions should be main-safe; each function that does blocking work moves itself off the main thread.

IO and Default share threads (the pool is named DefaultDispatcher-worker-N), which makes switching between them cheap. Room and Retrofit's suspend functions are already main-safe, so you can call them directly from viewModelScope.

13.6Cancellation & timeouts

Cancellation is cooperative: a coroutine is only cancelled at a suspension point (delay, withContext, yield…) or when it checks isActive/ensureActive(). A tight CPU loop that never suspends can't be cancelled.

🚫
Never swallow CancellationException

Cancellation is implemented with a special exception. A blanket catch (e: Exception) around suspending code catches it and keeps the coroutine running as a “zombie”. Catch specific exceptions, or rethrow: catch (e: Exception) { if (e is CancellationException) throw e; … }. Note that runCatching also catches it — be careful using it with suspend calls.

13.7Exception handling & supervisors

  • Inside a coroutine, use normal try/catch around the suspend call that may fail — this is the right tool 90% of the time.
  • An uncaught exception in launch propagates to the parent and cancels its siblings. In async, it's thrown again at await() (and still cancels the parent).
  • When children should fail independently (e.g. loading several widgets), use supervisorScope or a SupervisorJob. viewModelScope uses a SupervisorJob.
  • CoroutineExceptionHandler is a last-resort handler for uncaught exceptions in root launch coroutines (for logging/crash reporting).

13.8Shared mutable state

Coroutines on Dispatchers.Default run truly in parallel, so unsynchronized updates to shared variables lose writes. Options: confine the state to one thread, use atomics, or protect a critical section with a Mutex (a suspending lock — never use synchronized around suspend calls).

13.10Exercises

Exercise 1 — Parallel downloads Easy

Simulate downloading 5 files (each takes delay(300 * index)) in parallel with async, and print the total size and that the elapsed time is less than the sum of delays.

Exercise 2 — Retry with exponential backoff Medium

Write suspend fun <T> retryWithBackoff(times: Int, initialDelay: Long, block: suspend () -> T): T doubling the delay after each failure. Make sure cancellation isn't swallowed.

Exercise 3 — Fastest mirror wins Challenge

Query three “mirrors” with different latencies concurrently; return the first response and cancel the rest. Hint: select works, but a simpler route is a Channel or CompletableDeferred completed by whichever child finishes first, then coroutineContext.cancelChildren().
