15.1Type-safe builders (DSLs)

A domain-specific language is an API that reads like a description of the thing it builds. Kotlin DSLs are just regular code built from three features you already know: lambdas with receivers, extension functions and trailing lambdas. Gradle's build.gradle.kts, Ktor routing and Jetpack Compose are all Kotlin DSLs.

🏗️
DSL design checklist
  • Builders are mutable; the result is immutable (data classes, read-only lists).
  • Mark builder classes with your own @DslMarker annotation to stop scope leaks.
  • Give properties sensible defaults so the simple case is short.
  • Validate in build() with require.

15.2Annotations & reflection

Annotations attach metadata to code. Tools read them at compile time (Room's @Entity, Hilt's @Inject, kotlinx.serialization's @Serializable — processed by KSP or compiler plugins) or at runtime through reflection.

ℹ️
Use-site targets

A constructor val generates a parameter, a field, a getter (and maybe a setter). @field:, @get:, @param:, @property: choose where the annotation lands. Full reflection over Kotlin declarations (KClass.memberProperties, etc.) needs the kotlin-reflect library; on Android, prefer compile-time code generation (KSP) — it's faster and R8-friendly.

15.4Designing for Java callers

Libraries and large Android codebases often mix Kotlin and Java. A few annotations make your Kotlin API feel native from Java:

AnnotationEffect for Java
@JvmStaticCompanion/object function becomes a real static method
@JvmFieldExpose a property as a public field (no getter)
@JvmOverloadsGenerate overloads for parameters with default values
@JvmName("…")Rename the generated JVM method/class (e.g. @file:JvmName("Strings"))
@Throws(IOException::class)Declare checked exceptions so Java can catch them

What makes code testable

Inject dependencies through constructors (lesson 08), depend on interfaces, inject CoroutineDispatchers instead of hard-coding Dispatchers.IO, keep logic in pure functions and ViewModels rather than Activities. Testable code is almost always better-designed code.

15.6Kotlin Multiplatform (KMP)

Kotlin Multiplatform lets you share code — typically business logic, networking (Ktor), storage (Room KMP, SQLDelight), and even UI with Compose Multiplatform — across Android, iOS, desktop and web, while keeping full access to each platform's native APIs. Google officially supports KMP for sharing business logic between Android and iOS.

shared/src/ ├── commonMain/kotlin/ # pure Kotlin used by every platform │ └── Greeting.kt ├── androidMain/kotlin/ # Android-specific `actual` implementations │ └── Platform.android.kt └── iosMain/kotlin/ # iOS-specific `actual` implementations └── Platform.ios.kt

Common code declares what it needs with expect; each platform provides an actual:

commonMain
androidMain / iosMain

Start a project with the Kotlin Multiplatform wizard. Everything you've learned — coroutines, Flow, sealed classes, DSLs — works the same in commonMain.

15.7Professional habits & tooling

Formatting & linting

ktlint enforces the official code style; detekt finds code smells and complexity. Run both in CI — see the full setup on the Conventions page.

Explicit API mode

For libraries: kotlin { explicitApi() } forces visibility modifiers and return types on public declarations.

Documentation

Write KDoc on public APIs and generate docs with Dokka.

Benchmarks & profiling

Measure before optimizing: kotlinx-benchmark (JMH) on the JVM, Jetpack Macrobenchmark on Android.

Exercise 2 — Test-first: a password validator Medium

Exercise 3 — Test a debounced search with virtual time Challenge

First refactor lesson 14's SearchModel to receive its search function through the constructor — class SearchModel(scope: CoroutineScope, search: suspend (String) -> List<String>) — so a test can pass a fake. Then write a runTest test that types three characters quickly, advances virtual time with advanceTimeBy(250), and asserts that only one search was executed. Hint: pass the test's backgroundScope to the model and count calls in a fake search function.
