16.1Anatomy of an Android project

Here's the final project, TaskFlow, in Android Studio's Project view. Every modern Android app has the same skeleton:

TaskFlow/ ├── app/ # the application module │ ├── build.gradle.kts # module build script: SDK levels, dependencies │ ├── proguard-rules.pro # R8 shrinking rules for release builds │ └── src/ │ ├── main/ │ │ ├── AndroidManifest.xml # app identity, components, permissions │ │ ├── java/com/kotlinacademy/taskflow/ # Kotlin code (folder is called java/ for history) │ │ └── res/ # resources: strings, icons, themes │ ├── test/ # JVM unit tests (fast) │ └── androidTest/ # instrumented tests (on a device) ├── gradle/ │ ├── libs.versions.toml # version catalog: ALL dependency versions │ └── wrapper/ # pins the Gradle version ├── build.gradle.kts # root build script: plugins for all modules ├── settings.gradle.kts # repositories + list of modules ├── gradle.properties # build flags (memory, AndroidX…) ├── local.properties # SDK path on THIS machine — never commit └── gradlew / gradlew.bat # Gradle wrapper scripts

Android Studio's default Android view groups files by type rather than by folder. Switch with the dropdown above the project tree.

16.2Gradle, the Kotlin DSL & version catalogs

Gradle compiles Kotlin, processes resources, runs annotation processors (KSP), packages everything into an APK/AAB and signs it. Build scripts are written in Kotlin (.gradle.kts) — the DSL techniques from lesson 15 in action.

1. The version catalog

All versions live in one TOML file. Modules refer to them with type-safe accessors like libs.androidx.room.runtime, and Android Studio suggests upgrades right in this file.

2. The module build script

ConfigurationMeaning
implementationNeeded to compile and run the app
kspCode generator that runs during compilation (not shipped)
debugImplementationOnly in debug builds (e.g. Compose UI tooling)
testImplementationOnly for local JVM tests
androidTestImplementationOnly for instrumented device tests

16.3The manifest & app components

AndroidManifest.xml tells the operating system what your app contains and needs. Android has four kinds of components — entry points the system can start independently:

📱 Activity

A screen the user interacts with. Modern apps often have a single Activity hosting Compose navigation.

⚙️ Service

Long-running work without UI (music playback, foreground location). For deferrable background work, prefer WorkManager (lesson 19).

📡 BroadcastReceiver

Reacts to system-wide events (boot completed, timezone changed, alarm fired).

🗂 ContentProvider

Shares structured data with other apps (contacts, media). Also used by libraries for start-up initialization.

The MAIN/LAUNCHER intent filter puts the activity's icon on the home screen. android:exported must be set explicitly for any component with an intent filter.

16.4The Activity lifecycle

Your app doesn't control when it runs — the system does. As the user opens your app, switches away, rotates the phone or gets a call, the Activity moves through lifecycle states and Android calls the matching callbacks:

CallbackWhenTypical use
onCreateActivity createdsetContent { }, one-time setup
onStart / onStopBecomes visible / invisibleStart/stop UI updates, location, sensors
onResume / onPauseGains / loses focusCamera preview, animations
onDestroyFinishing or being recreatedFinal cleanup (rarely needed)

Configuration changes & process death

Rotating the screen, changing language or toggling dark mode is a configuration change: by default the Activity is destroyed and recreated. Separately, when your app is in the background, the system may kill the whole process to free memory, and recreate it when the user returns. Your app must survive both:

Where state livesSurvives rotationSurvives process deathUse for
remember { } in Compose❌❌Transient UI details
rememberSaveable { }✅✅ (small, Bundle-able)Text field contents, selected tab, dialog shown
ViewModel✅❌ (unless using SavedStateHandle)Screen state, loaded data
Database / DataStore✅✅User data, settings
🧪
Test process death

Put your app in the background, then run adb shell am kill com.kotlinacademy.taskflow.debug and reopen it from Recents. Or enable Developer options → Don't keep activities. Many real-world bugs appear only here.

16.5Resources & localization

Everything that isn't code lives in res/: strings, colors, images (prefer vector drawables), fonts. Never hard-code user-visible text — put it in strings.xml so it can be translated. Android picks the best match for the current device using qualifiers on folder names.

QualifierExample folderChosen when…
Language / regionvalues-vi, values-pt-rBRDevice language matches
Night modevalues-nightDark theme is on
Screen widthvalues-w600dpAt least 600dp wide (tablets, foldables)
API levelmipmap-anydpi-v26Android 8.0+
Densitydrawable-xxhdpiFor bitmaps only; vectors scale automatically

16.7Runtime permissions

Permissions protecting private data or sensitive features (“dangerous” permissions: camera, location, contacts, notifications on Android 13+) must be declared in the manifest and requested at runtime. Ask in context — when the user taps the feature that needs it — and handle refusal gracefully.

ℹ️
Permission etiquette
  • Request the minimum. Many features don't need a permission at all (the photo picker above needs none).
  • If the user denies twice, the system stops showing the dialog; offer a button to Settings instead of nagging.
  • Always check before use: ContextCompat.checkSelfPermission(context, permission) == PERMISSION_GRANTED.

16.8Context & Logcat

Context is your handle to the system: resources, files, databases, system services, starting activities. There are two you'll use:

  • Activity context — tied to a screen, carries the theme; needed for UI things like dialogs. Never store it in a long-lived object (singleton, ViewModel): it leaks the whole screen.
  • Application context — lives as long as the app. Safe to keep; that's what Hilt injects with @ApplicationContext.

Logcat (bottom tool window) shows system and app logs. Filter with queries like package:mine level:debug tag:Lifecycle.

16.9Exercises

Exercise 1 — Lifecycle detective Easy

Add the lifecycle logging from 16.4 to a new Empty Activity project. Predict the callbacks for each scenario, then verify in Logcat: (a) press Home, (b) return from Recents, (c) rotate, (d) press Back.

Expected

(a) onPause → onStop · (b) onRestart → onStart → onResume · (c) onPause → onStop → onDestroy → onCreate → onStart → onResume · (d) onPause → onStop → onDestroy. Note: since Android 12, Back on the root launcher activity moves the task to the background instead of finishing it, so you may see only onPause → onStop.

Exercise 2 — Speak Vietnamese (or your language) Medium

Move all hard-coded strings of your Empty Activity app into strings.xml, then add a translation: right-click strings.xml → Open Translations Editor → 🌐 add a locale. Switch the emulator language (Settings → System → Languages) and watch the app change without code changes.

Exercise 3 — Share button Challenge

Add a Compose button that shares “I'm learning Kotlin at Kotlin Academy!” via the system share sheet, and a second button that opens https://kotlinlang.org. Get the context inside a composable with LocalContext.current.
