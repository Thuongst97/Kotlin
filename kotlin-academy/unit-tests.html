Unit Tests (UTs): Setup & Run

A hands-on guide to unit testing Kotlin, from an empty folder to a green CI badge. You'll set up tests in a plain Kotlin/JVM project and in an Android app, run them from the IDE and the command line, test coroutines and Flows, use fakes and mocks, measure coverage and run everything in CI. Every file shown here is real: the sample project and TaskFlow run these exact tests on every push.

You will be able to

  • Add unit tests to a Kotlin/JVM or Android project
  • Run all tests, one class or one method, from the IDE and Gradle
  • Read test reports and debug a failing test
  • Test suspend functions and Flows with virtual time
  • Choose between fakes and mocks
  • Measure coverage with Kover and run tests in CI

C.1What a unit test is (and where it lives)

A unit test (UT) checks one small piece of behaviour, like a function, a class or a ViewModel, without its real dependencies. It runs on your computer's JVM in milliseconds, with no device, network or database. That speed is the point: you can run hundreds of them every time you save.

KindFolderRuns onSpeedGradle task
Unit test (this page)src/testYour computer's JVMms per testtest (JVM) · testDebugUnitTest (Android)
Instrumented testsrc/androidTestEmulator or deviceseconds per testconnectedDebugAndroidTest

Good unit tests are F.I.R.S.T.:

Fast & Isolated

Milliseconds each. No shared state between tests, so order never matters. Each test builds what it needs.

Repeatable

Same result every run, on every machine. No real clocks, network, random numbers or Thread.sleep.

Self-validating

Pass or fail on its own through assertions. Nobody reads printed output to decide.

Timely

Written with the code (or before it, with TDD), not months later.

C.2What a test framework actually does

Before adding JUnit, here's the whole idea in plain Kotlin. A test framework finds test functions, runs each one in isolation, treats a thrown AssertionError as a failure, and reports the results. Press ▶ Run to see it work:

JUnit does the same job with more features: it finds tests through @Test annotations, creates a new instance of the test class for every test (that's the isolation), runs setup and teardown hooks, and writes HTML and XML reports that IDEs and CI servers understand.

C.3Setup: a Kotlin/JVM project with Gradle

Use this for libraries, back-end code, command-line tools, or to practise testing without Android. You need a JDK 17 or 21 and IntelliJ IDEA or Android Studio.

  1. Create the project. In IntelliJ IDEA choose File → New → Project → Kotlin, set Build system: Gradle and DSL: Kotlin. From a terminal you can run gradle init and pick Application → Kotlin. Or clone the ready-made sample: samples/unit-testing in this repository.
  2. Check the folder layout. Production code lives in src/main/kotlin and tests in src/test/kotlin. Use the same package in both, so tests can reach internal declarations.
  3. Add the test dependencies and enable JUnit 5 in build.gradle.kts (below).
  4. Sync Gradle (the 🐘 icon, or Ctrl+Shift+O / ⇧⌘I), then write your first test (C.5).

ℹ️
JUnit 4 or JUnit 5?

On the JVM, use JUnit 5 (the "Jupiter" API) as shown. Android local tests run on JUnit 4 by default, and that's what the Android templates and TaskFlow use. With kotlin.test your test code looks the same either way: only the imports for advanced features (rules, parameterized tests) differ.

C.4Setup: an Android project

A new Android Studio project already includes JUnit 4 and an ExampleUnitTest in app/src/test. For real projects, add coroutine and Flow testing and declare everything in the version catalog. These are TaskFlow's actual entries:

Android adds one test task per build variant: testDebugUnitTest, testReleaseUnitTest, and so on. ./gradlew test runs all of them, which usually means running every test twice. Run the debug one while you work.

⚠️
Local tests can't use real Android classes

Local tests compile against a stub android.jar whose methods throw. Keep Android types out of the code you unit-test: ViewModels, repositories and domain logic should depend on your own interfaces. When you really need Android framework behaviour on the JVM, use Robolectric; otherwise write an instrumented test.

Name tests after behaviour

Backtick names read like a specification: `total never goes below zero`. They work in JVM and Android local tests. In instrumented tests, use camelCase_withUnderscores instead: spaces in method names are only supported from API 30.

Arrange · Act · Assert

Build the inputs, call the code once, then check the outcome. One behaviour per test, so a failure tells you exactly what broke.

Fresh state per test

@BeforeTest (JUnit's @Before/@BeforeEach) runs before every test. JUnit also creates a new instance of the class for each test, so fields are never shared.

Assert the message too

assertFailsWith returns the exception, so you can check that the error message will actually help whoever sees it.

kotlin.testChecks
assertEquals(expected, actual)Equality, with a readable "expected … but was …" message. Expected comes first.
assertTrue(x) / assertFalse(x)Booleans. Pass a message for clarity: assertTrue(ok, "cart should be empty")
assertNull(x) / assertNotNull(x)Nullability. assertNotNull returns the value smart-cast to non-null.
assertIs<T>(x)Type, returning x smart-cast to T. Great for sealed UI states.
assertContains(list, x)Collections, strings and ranges
assertFailsWith<E> { … }The block throws E; returns the exception
fail("message")Unconditional failure, e.g. in a branch that must never run

C.6Run tests in Android Studio or IntelliJ IDEA

  1. One test or one class: click the green ▶ gutter icon next to a test function or class and choose Run. Shortcut with the caret inside it: Ctrl+Shift+F10 (Windows/Linux) or ⌃⇧R (macOS).
  2. A whole package or every test: right-click the test (or kotlin/java) folder in the Project view and choose Run 'Tests in …'.
  3. Read the results: the Run window shows a tree of tests. ✔ passed, ✘ failed, with the assertion message, a stack trace you can click, and <Click to see difference> for side-by-side expected/actual.
  4. Fix and re-run: use Rerun Failed Tests in the Run window, or Ctrl+F5 / ⌘R to repeat the last run.
  5. Debug: set a breakpoint in the test or the code under test, then choose Debug from the gutter icon. Step through exactly as in the debugger lesson.
  6. Coverage: choose Run … with Coverage from the gutter menu. Covered lines get a green bar in the editor and the Coverage window lists percentages per package.
💡
Run the tests the way CI does

The IDE runs tests through Gradle by default (Settings → Build, Execution, Deployment → Build Tools → Gradle → Run tests using: Gradle). Keep it that way: then a test that passes in the IDE also passes on the command line and in CI.

Why didn't my tests run?

Gradle skips a test task whose inputs haven't changed (UP-TO-DATE). That's a feature: nothing changed, so the results can't have either. Add --rerun to force a run, for example while checking a test for flakiness.

C.8Testing suspend functions with runTest

A test function can't call suspend code directly. Wrap the body in runTest { } from kotlinx-coroutines-test. It runs coroutines on a test scheduler with virtual time: delay(1_000) completes instantly, but currentTime still advances by 1 000 ms. A test of a 10-second timeout finishes in milliseconds and gives the same result every time.

currentTime is marked experimental in kotlinx-coroutines-test, so the class opts in with @OptIn(ExperimentalCoroutinesApi::class); without it, the compiler prints a warning. The second test proves the prices are fetched in parallel, something that's hard to check with real time. If someone "simplifies" quote to a sequential map { api.priceOf(it) }, currentTime becomes 3 000 and the test fails.

On Android: replace Dispatchers.Main

ViewModels launch in viewModelScope, which uses Dispatchers.Main, and that dispatcher doesn't exist on the JVM. Without a replacement, tests fail with "Module with the Main dispatcher is missing". A JUnit 4 rule swaps in a test dispatcher for each test. This is TaskFlow's:

ToolUse it to
runTest { }Run a test body as a coroutine with virtual time. Fails if coroutines are still running at the end.
currentTimeRead the virtual clock (ms)
advanceTimeBy(ms) / advanceUntilIdle()Move virtual time forward, or run everything that's scheduled
runCurrent()Run tasks scheduled for the current moment
StandardTestDispatcher()New coroutines queue until the test advances time. Gives precise control.
UnconfinedTestDispatcher()New coroutines start eagerly. Simplest for collecting StateFlows in ViewModel tests.
backgroundScopeLaunch never-ending collectors that are cancelled automatically when the test ends

C.9Testing Flows with Turbine

Turbine turns a Flow into a queue you can assert on one event at a time. If an unexpected item, error or completion arrives, the test fails with a clear message.

✅
Prefer fakes

The Android testing guide recommends fakes over mocks. A fake tests what happened (state), so it survives refactoring; a mock tests how it happened (calls), so it breaks when you change the internals. Design for it: depend on interfaces (ideally fun interfaces) and inject them through the constructor. Reach for MockK for classes you don't own, or when the interaction itself is the behaviour (e.g. "the analytics event is sent exactly once").

Coverage is a flashlight, not a score

Coverage shows which code no test executes, and that's useful for finding gaps. High coverage doesn't prove the tests check anything: a test without assertions can still reach 100 %. Aim for well-tested domain logic, ViewModels and mappers, and set a realistic gate (60–80 %) so coverage doesn't silently drop.

C.15A good unit test: checklist

  • Tests live in src/test, in the same package, named …Test
  • Each test checks one behaviour and its name says which
  • Arrange · Act · Assert is visible at a glance; no loops or ifs deciding what to assert
  • No real network, disk, database, clock, randomness or Thread.sleep
  • Suspend code uses runTest; ViewModels use MainDispatcherRule
  • Dependencies are injected interfaces, replaced by fakes; mocks only when interactions matter
  • Error cases are tested too, including the error messages
  • The whole suite passes with ./gradlew test (or testDebugUnitTest) and runs in CI on every push
  • A test that fails points straight at the problem, without a debugger
