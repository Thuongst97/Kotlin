20.2Unit-testing ViewModels

🧪 New to unit tests? Reference C · Unit Tests: Setup & Run walks through setup, running from the IDE and the command line, reports, coverage and CI step by step.

Three ingredients make ViewModel tests fast and reliable:

  1. Fakes for dependencies — small in-memory implementations of your interfaces.
  2. A MainDispatcherRule replacing Dispatchers.Main (which doesn't exist on the JVM) with a test dispatcher.
  3. runTest for coroutines with virtual time, plus Turbine for Flows.

20.3Room & Compose UI tests

Instrumented tests run on a device with real Android classes. For Room, use an in-memory database; for Compose, createComposeRule() lets you set content, find nodes by text or content description, perform clicks and assert.

Testing the stateless TasksContent needs no ViewModel, database or Hilt — another payoff of state hoisting.

20.4Debugging toolkit

🐞 Debugger

Click the gutter to set a breakpoint, run with Debug (Shift+F9) or Attach Debugger to Android Process. Step over/into, inspect variables, Evaluate Expression (Alt+F8). Right-click a breakpoint for conditions and non-suspending log points. The Coroutines tab shows coroutine stacks.

📜 Logcat

Filter with package:mine level:error. Crashes show as red FATAL EXCEPTION — read the first “Caused by” line that points to your package.

🧱 Layout Inspector

Inspect the live Compose tree, parameters and recomposition counts — spot composables that recompose too often.

🗄 App Inspection

Database Inspector (live SQL against Room), Network Inspector (requests/responses), Background Task Inspector (WorkManager).

📈 Profiler

CPU, memory, and energy over time. Use the profileable release build for realistic numbers; system traces find jank.

🚨 StrictMode & LeakCanary

StrictMode flags disk/network work on the main thread in debug builds; the LeakCanary library detects leaked Activities automatically.

20.5Release builds & R8

Release builds enable R8, which removes unused code (shrinking), renames classes (obfuscation), and optimizes bytecode; isShrinkResources also removes unused resources. Apps commonly get much smaller and faster.

R8 only removes what it can prove is unused. Code reached via reflection (some serialization, JNI) needs keep rules. Libraries ship their own rules; add yours only for your reflective code:

🧪
Always test the release build

R8 bugs only show up in release. Install it on a device (./gradlew installRelease with a signing config) and click through every screen before publishing. Upload the generated mapping.txt to Play Console so crash stack traces are de-obfuscated.

20.6Signing your app

Every APK/AAB must be signed. Debug builds use an automatic debug key; releases need your upload key. Create it once and keep it safe — and never commit it to git.

🔑
Play App Signing

Google Play stores your real app signing key and re-signs your bundles; you only sign uploads with your upload key. If you lose the upload key, Google can reset it. That's why Play App Signing is mandatory for new apps — and a relief.

20.7Publishing on Google Play

  1. Build an Android App Bundle./gradlew bundleRelease → app/build/outputs/bundle/release/app-release.aab. Play generates optimized APKs per device from it.
  2. Create a developer accountAt play.google.com/console (one-time registration fee, identity verification).
  3. Create the app & store listingName, short and full description, icon (512×512), feature graphic (1024×500), phone screenshots, category, contact email.
  4. Complete “App content”Privacy policy URL, Data safety form (what data you collect and why), content rating questionnaire, target audience, ads declaration.
  5. Test before productionUpload to Internal testing (up to 100 testers, available in minutes), then Closed/Open testing. New personal developer accounts must run a closed test with a minimum number of testers for a period before production access — check the current requirement in Play Console.
  6. Release to productionUse a staged rollout (e.g. 10% → 50% → 100%) and watch the Android vitals dashboard for crashes and ANRs before widening.
📅
Keep your app updatable

Increase versionCode for every upload. Google Play requires new apps and updates to target a recent API level, so plan a targetSdk bump every year.

20.9Pre-launch checklist

  • All unit and UI tests pass in CI.
  • Release build tested on a real device (R8 enabled).
  • Survives rotation, dark mode, the largest font size, and process death.
  • Works offline and shows helpful errors when the network fails.
  • No debug logging of private data; no secrets in the APK.
  • Runtime permissions requested in context, with graceful denial.
  • TalkBack can operate every screen; touch targets ≥ 48dp.
  • versionCode bumped, mapping file uploaded, staged rollout planned.

20.10Exercises

Exercise 1 — Break it, then catch it Easy

In TaskFlow, change the ACTIVE branch of TaskFilter.matches to return true. Run ./gradlew testDebugUnitTest, read which test fails and why, then revert. This is how tests protect you.

Exercise 2 — A test for import failure Medium

Add a unit test asserting that isImporting is true while an import is in progress. Hint: make the fake's importSampleTasks() suspend on a CompletableDeferred that the test completes later.

Exercise 3 — Ship to internal testing Challenge

Change TaskFlow's applicationId to your own (e.g. com.yourname.taskflow), create an upload key, build bundleRelease, and publish it to an Internal testing track. Install it from the Play Store link on your phone.
