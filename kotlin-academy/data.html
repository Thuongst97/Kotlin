19.2Room: a type-safe SQLite database

Room has three parts. KSP generates the implementation at compile time — and checks your SQL against your schema, so a typo in a query is a build error, not a crash.

@Entity

A data class = a table. Each property = a column.

@Dao

An interface of queries. Return Flow to observe, suspend for one-shot operations.

@Database

Lists entities and version; gives access to DAOs.

⚡
Threading is handled for you

Room runs suspend DAO functions and Flow queries on its own background executor, so they're main-safe: call them straight from viewModelScope. Room even refuses to run blocking queries on the main thread.

Relations, indices & type converters

Migrations

When you change an entity, bump the database version and tell Room how to upgrade existing users' data. Simple additions can be automatic; anything else needs a manual migration. Never ship fallbackToDestructiveMigration() in production — it deletes user data.

Auto-migrations need the exported schema JSON files. TaskFlow configures room { schemaDirectory("$projectDir/schemas") } and commits them to git.

19.3Preferences DataStore

DataStore stores key-value pairs asynchronously and transactionally, and exposes them as a Flow — the settings screen and the rest of the app update instantly when a value changes.

19.4Networking with Retrofit & kotlinx.serialization

Retrofit turns an annotated Kotlin interface into an HTTP client. kotlinx.serialization converts JSON to Kotlin classes using compile-time generated code (no reflection). OkHttp does the actual HTTP work and lets you add interceptors for logging, auth headers, caching.

  1. Permission & pluginsAdd <uses-permission android:name="android.permission.INTERNET" /> to the manifest and the plugin alias(libs.plugins.kotlin.serialization); dependencies: retrofit, converter-kotlinx-serialization, kotlinx-serialization-json, logging-interceptor.

Networking hygiene
  • HTTPS only (cleartext HTTP is blocked by default since Android 9).
  • Never log bodies or auth headers in release builds — note the BuildConfig.DEBUG guard.
  • Don't hard-code API keys in the app; anything in the APK can be extracted. Keep secrets on your server.

19.5The offline-first repository

Offline-first means the local database is the source of truth: the UI always reads from Room, and the network only writes into Room. The app works without a connection, starts instantly, and never shows a blank screen while loading.

Syncing in real apps

A production sync engine also queues local changes while offline and pushes them later (a “pending changes” table plus a WorkManager job with a network constraint), and resolves conflicts (e.g. last-write-wins by updatedAt). The offline-first guide covers these strategies.

19.6Background work with WorkManager

Coroutines in viewModelScope stop when the screen goes away. For work that must happen even if the app is closed or the phone restarts — sync, uploads, reminders — use WorkManager. It respects battery-saving rules and supports constraints (network, charging), retries with backoff, chaining and periodic work.

19.7Exercises

Exercise 1 — Notes database Easy

Create a NoteEntity(id, text, pinned, createdAt), a DAO that returns pinned notes first as a Flow, and a database. Write an instrumented test using Room.inMemoryDatabaseBuilder.

Exercise 2 — Quote of the day Medium

Call https://dummyjson.com/quotes/random (returns {"id":1,"quote":"…","author":"…"}) with Retrofit, cache the last quote in DataStore, and show it on screen. When offline, show the cached quote plus a small “offline” label.

Exercise 3 — Daily cleanup worker Challenge

Add a periodic CleanupWorker to TaskFlow that deletes tasks completed more than 30 days ago. You'll need a completed_at column (database version 2 + migration), a DAO query, and a unique periodic work request enqueued in TaskFlowApp.onCreate with ExistingPeriodicWorkPolicy.KEEP.
