Lesson 18 · Android with Kotlin

App Architecture: MVVM, Hilt & Navigation

A screen that works is the beginning. An app that keeps working as it grows needs architecture: clear layers, one source of truth, state that flows in one direction, and dependencies that are injected rather than created. This is Google's recommended architecture — and exactly how TaskFlow is built.

⏱ 70 min🎯 Advanced🏗 Uses TaskFlow's real code

You will be able to

  • Separate UI, domain and data layers
  • Write ViewModels exposing StateFlow UI state
  • Apply unidirectional data flow (UDF)
  • Model one-off events correctly
  • Inject dependencies with Hilt
  • Navigate type-safely between screens with arguments

18.2ViewModel & unidirectional data flow

A ViewModel survives configuration changes and owns viewModelScope, which is cancelled when the screen is gone for good. It exposes one immutable UI state as a StateFlow, and public functions for user actions:

→
ViewModelcombine → TasksUiState
→
Screenrenders state
→
User actionviewModel.toggleDone(task)
↺
✅
Why this design works
  • Single source of truth: tasks come only from the database Flow. Toggling a task writes to the database; the new list flows back automatically. No “remember to refresh the UI”.
  • Derived state: counts, filtering and sorting are computed, never stored separately — so they can't get out of sync.
  • Testable: the ViewModel depends on interfaces; tests pass fakes (see TasksViewModelTest in the final project).
🚫
Never put these in a ViewModel

References to Activity, Context (except via AndroidViewModel/application context), Views or composables. The ViewModel outlives them — that's a memory leak.

18.3State vs one-off events

Most things are state (what's on screen). Some are events that should happen once: show a snackbar, navigate after saving. Two good patterns:

Model it as state

The edit screen sets isSaved = true in its UI state; the screen reacts with LaunchedEffect(state.isSaved) { if (it) onDone() }. Survives rotation, easy to test. Google's preferred approach.

A Channel of events

For fire-and-forget messages like “Task deleted — Undo”, TaskFlow uses Channel(BUFFERED).receiveAsFlow(): each event is delivered to exactly one collector, and buffered if the UI isn't collecting at that moment.

18.4Repositories: the single source of truth

A repository hides where data comes from. ViewModels see an interface with Flows and suspend functions; the implementation coordinates Room, the network, WorkManager… Swap the implementation for a fake in tests, or for a different backend later, without touching the UI.

The implementation is shown in full in lesson 19. Note the mapping: Room's TaskEntity and the network's TodoDto never leave the data layer — the rest of the app only sees the domain Task.

18.5Dependency injection with Hilt

Without DI, every class creates its own collaborators: TasksViewModel would build a repository, which builds a database and a Retrofit client… Hard to test and wasteful. With Hilt (built on Dagger), you declare what each class needs in its constructor and Hilt builds and delivers the whole object graph at compile time.

  1. Add the plugin & dependencies
  2. Annotate the Application and Activity
  3. Constructor injection for your own classes
  4. Modules for things you can't annotate (third-party classes, interfaces)
  5. Get a ViewModel in a composable

ℹ️
Hilt errors are compile errors

If something can't be provided (“[Dagger/MissingBinding] TaskRepository cannot be provided without an @Provides-annotated method”), the build fails with a path through the graph. Read it bottom-up to find who needs what. That's a feature: DI mistakes never reach users.

18.6Type-safe Navigation Compose

Navigation Compose 2.8+ uses Kotlin types as routes. Each destination is a @Serializable object or data class; its properties are the arguments. No string routes, no manual argument parsing.

Navigation guidelines
  • Pass IDs, not whole objects. The next screen loads the data from the repository (single source of truth).
  • Screens don't receive the NavController; they expose callbacks (onOpenTask). Navigation stays in one place and screens stay testable.
  • Add the kotlinx.serialization plugin: alias(libs.plugins.kotlin.serialization).

18.7Architecture checklist

  • Each screen has a ViewModel exposing a single StateFlow<UiState> built from repository Flows.
  • UI state is an immutable data class (or sealed interface); updates use copy / update { }.
  • Composables are split into a stateful entry point and stateless content.
  • The data layer exposes domain models; entities/DTOs stay inside it.
  • All dependencies arrive through constructors; Hilt wires them.
  • Suspend functions are main-safe; no GlobalScope, no runBlocking in app code.
  • Navigation uses typed routes and passes IDs.
  • ViewModels have unit tests using fakes.
