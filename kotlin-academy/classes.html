Lesson 08 · Object-Oriented Kotlin

Classes, Objects & Interfaces

Classes bundle data and behaviour into your own types. Kotlin keeps the good parts of object-oriented programming and removes the ceremony: constructors and properties in one line, classes final by default, and interfaces that can carry default behaviour.

⏱ 60 min🎯 Intermediate▶ All examples are runnable

You will be able to

  • Declare classes with primary constructors
  • Use init blocks and secondary constructors
  • Write custom getters/setters and backing fields
  • Control access with visibility modifiers
  • Build hierarchies with open, abstract, override
  • Design with interfaces and composition

8.1Classes & the primary constructor

A class is a blueprint; an object (instance) is a thing built from it. The primary constructor sits right after the class name. Prefixing a parameter with val or var turns it into a property.

☕
Coming from Java

That one line class Dog(val name: String, var age: Int) replaces a Java class with two fields, a constructor, two getters and one setter. Properties compile to a private field plus getName()/getAge()/setAge() — which is exactly what Java code calling your Kotlin class sees.

8.2init blocks, defaults & secondary constructors

Validation or setup logic goes in an init block, which runs as part of the primary constructor. Default values usually make secondary constructors unnecessary — but they exist when you need them.

Initialization order: primary constructor parameters → property initializers and init blocks, top to bottom in the class body → secondary constructor body.

8.3Properties: getters, setters & backing fields

Properties can have custom accessors. Inside a setter, field refers to the stored value (the backing field). A property with only a getter and no stored value is a computed property.

💡
Minimize the surface

Start everything private and widen only when needed. In multi-module Android projects, internal is excellent for hiding implementation classes (e.g. a RoomTaskDao) while exposing only interfaces.

☕
Coming from Java

Kotlin's default is public, not package-private, and there is no package-private visibility at all. internal is the closest replacement.

8.5Inheritance: open and override

Classes are final by default. To allow subclassing, mark the class open; to allow a member to be overridden, mark it open too. Overriding members must say override.

⚠️
Don't call open members from constructors

The base class initializes before the subclass. If the base constructor calls an open function that the subclass overrides, the override runs while the subclass's properties are still uninitialized (even non-null ones may be null at that moment). The IDE warns about this — listen to it.

8.6Abstract classes

An abstract class can't be instantiated; it's a partial implementation meant to be completed by subclasses. Abstract members have no body and are implicitly open.

8.7Interfaces

An interface is a contract: a set of members a type promises to provide. Interfaces may contain default implementations and abstract properties, but no state (no backing fields). A class can implement many interfaces but extend only one class.

Functional (SAM) interfaces

An interface with exactly one abstract method can be declared fun interface, which lets callers implement it with a lambda:

Abstract classInterface
State (fields)✅ yes❌ no (only abstract or computed properties)
Constructor✅ yes❌ no
Multiple inheritance❌ one superclass✅ many interfaces
Use whenSharing state + code among closely related typesDefining capabilities / contracts (repository, listener, strategy)

8.8Composition over inheritance

Deep inheritance trees become rigid: a change in a base class ripples into every subclass. Most modern Kotlin code — and Android architecture — prefers composition: build objects from smaller collaborators passed through the constructor, typed by interfaces.

🎭
Analogy

Inheritance is like a family tree — you're stuck with your ancestors. Composition is like a band — you can swap the drummer without rebuilding the band. This idea, passing dependencies in through the constructor, is called dependency injection; lesson 18 automates it with Hilt.

8.9Exercises

Exercise 1 — Bank account Easy

Create BankAccount(owner: String) with a balance that can only change through deposit and withdraw. Withdrawing more than the balance must fail by returning false. Keep a read-only list of transaction descriptions.

Exercise 2 — Employees & payroll Medium

Create an abstract Employee(name) with abstract monthlyPay(): Double. Implement Salaried(name, annual) and Hourly(name, rate, hours) (overtime above 160 hours pays 1.5×). Print a payroll sorted by pay.

Exercise 3 — Pluggable notifications Challenge

Design a Notifier interface and two implementations (EmailNotifier, SmsNotifier). Create a CompositeNotifier that forwards to a list of notifiers, and a QuietHoursNotifier that wraps another notifier and drops messages during quiet hours (22–7). Use composition only — no inheritance between implementations.

This is the Decorator pattern (QuietHours) plus the Composite pattern — both are natural with interfaces and constructor injection.
