Null Safety

Tony Hoare called the null reference his “billion-dollar mistake”. Kotlin fixes it in the type system: the compiler knows which values may be null and forces you to handle them — so NullPointerException becomes a compile error instead of a crash in your users' hands.

⏱ 40 min🎯 Beginner⭐ The most important Kotlin feature

You will be able to

  • Distinguish String from String?
  • Use ?., ?:, as? and ?.let
  • Rely on smart casts after null checks
  • Know why !! is a code smell
  • Initialize properties with lateinit and lazy
  • Handle nulls coming from Java code

6.1Nullable and non-nullable types

By default, a type cannot hold null. Add ? to the type to allow it. String and String? are different types, and the compiler won't let you call methods on a String? without handling the null case.

6.2The safe-call operator ?.

a?.b means: “if a is not null, evaluate a.b; otherwise the whole expression is null.” Calls can be chained — the first null short-circuits the rest.

6.3The Elvis operator ?:

a ?: b returns a if it isn't null, otherwise b. (Tilt your head: ?: looks like Elvis's hairstyle.) Because return and throw are expressions, the right side can also exit the function.

6.4Null checks & smart casts

After you check that a value isn't null, the compiler smart-casts it to the non-null type for the rest of that scope.

⚠️
Smart casts need stability

The compiler only smart-casts values that can't change between the check and the use: local vals, local vars not captured by a lambda that modifies them, and val properties without custom getters in the same module. For a mutable class property (var), copy it into a local val first, or use ?.let.

6.5?.let, safe casts as? and null-aware helpers

value?.let { … } runs the block only when the value is non-null; inside, it is non-null. as? casts safely, returning null instead of throwing ClassCastException.

6.6The not-null assertion !!

value!! converts a nullable value to non-null — and throws NullPointerException if it's null. It means “trust me, compiler”. You're turning off the safety net.

🚫
Treat !! as a code smell

Every !! is a potential crash. Prefer, in order: making the type non-null in the first place, ?: with a default, ?: return, ?.let, or requireNotNull(x) { "message" } / checkNotNull which at least throw with a useful message. A good codebase has almost no !!.

6.7Deferred initialization: lateinit and lazy

Sometimes a property can't be initialized in the constructor, but you don't want to make it nullable just for that.

lateinit var

“I promise to assign this before reading it.” Only for non-null, non-primitive vars. Reading it too early throws UninitializedPropertyAccessException. Common in tests (@Before) and dependency injection.

val … by lazy { }

Computed on first access, then cached. Thread-safe by default. Ideal for expensive objects that may not be needed.

6.8Java interop: platform types

Java has no nullability in its type system, so a String returned by Java code might be null. Kotlin represents such values as platform types, shown in IDE hints as String!: you may treat them as nullable or non-null — and you're responsible if you're wrong.

💡
Annotated Java is safe

When Java code uses nullability annotations (@Nullable/@NonNull from JetBrains, AndroidX, JSpecify…), Kotlin sees real String?/String types. The Android SDK and AndroidX are annotated, which is why Android APIs mostly feel null-safe in Kotlin.
