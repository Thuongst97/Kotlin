Coding Conventions, Rules & Best Practices

Yes — Kotlin has coding conventions, and unlike C++ there is one official guide that the whole ecosystem follows. This page collects the official conventions, a numbered rule set you can adopt as a team standard (in the spirit of MISRA/AUTOSAR for C++), the best practices for coroutines, Android, Compose, testing and security — and shows how to enforce all of it automatically with ktlint and detekt, exactly as the final project does.

Apply the official style in 10 seconds

IntelliJ IDEA / Android Studio: Settings → Editor → Code Style → Kotlin → Set from… → Kotlin style guide. Then enable Settings → Editor → Inspections → General → Incorrect formatting. Add kotlin.code.style=official to gradle.properties so everyone who opens the project gets the same style.

B.2Coming from C++: MISRA, AUTOSAR & Core Guidelines

C++ has no official style; teams adopt the C++ Core Guidelines, the Google C++ Style Guide, or — in automotive and safety-critical work — MISRA C++ and AUTOSAR C++14. Many MISRA/AUTOSAR rules exist to prevent undefined behaviour that simply cannot happen in Kotlin. The table maps the familiar rule themes to how Kotlin handles them:

No implicit narrowing / widening conversionsNo implicit numeric conversions at all (Int → Long needs toLong())🟢 Compiler
switch must handle all caseswhen over enum/sealed/Boolean must be exhaustive (expressions and statements)🟢 Compiler
No goto; restricted breakNo goto; only labeled break/continue/return🟢 Language
No preprocessor macrosNo preprocessor; use const val, inline functions, build variants🟢 Language
RAII, no raw new/deleteGarbage collection for memory; use { } for resources (files, sockets)🟢 Runtime + 🟡 convention

Don't catch everything / don't swallow errorsNo checked exceptions; catch narrowly, never swallow🔵 detekt TooGenericExceptionCaught, SwallowedException, EmptyCatchBlock
Limit function size and complexitySmall, single-purpose functions🔵 detekt LongMethod, CyclomaticComplexMethod, NestedBlockDepth

Acronyms

The two guides differ slightly. Kotlin conventions: two-letter acronyms stay uppercase (IOStream), longer ones capitalize only the first letter (XmlFormatter, HttpInputStream). Android guide: treat every acronym as a word (XmlHttpRequest, customerId, supportsIpv6OnIos). Pick one per project — Android apps should follow the Android guide.

Test function names

Kotlin allows backtick names with spaces in tests only: fun `adds tax to the subtotal`(). They work in JVM unit tests (src/test), but Android's runtime supports them only from API 30, so the Android guide forbids spaces — use underscores in instrumented tests: fun upsert_updatesExistingRow(). TaskFlow follows exactly this split.

Choose good names

  • Classes are nouns (PersonReader); functions are verbs (readPersons).
  • The name says whether a function mutates or returns a new value: sort() sorts in place, sorted() returns a copy.
  • Avoid meaningless words: Manager, Wrapper, Helper, Util, Data, Info.
  • Booleans read as questions: isVisible, hasError, canEdit, shouldRetry.
  • No Hungarian or member prefixes (mName, sInstance, strTitle) — the type system and IDE already tell you.

B.5Formatting rules

Layout

  • 4 spaces per indent level; no tabs.
  • Opening brace at the end of the line (“K&R / Egyptian” style); closing brace on its own line.
  • One statement per line; omit semicolons.
  • Line limit: 100 columns (Android guide). Package and import lines are exempt.
  • Imports: single ASCII-sorted list, no wildcard imports (Android guide).
  • Never align code horizontally — renaming must not force re-formatting other lines.

Whitespace

  • Spaces around binary operators a + b, but not around ..: 0..i.
  • No space around unary operators a++, !done.
  • Space after if, when, for, while; none before ( in calls/declarations.
  • No spaces around ., ?., ::, <T>, or before ? in String?.
  • Colon: val x: Int (no space before) but class A : B (space before when separating type/supertype or after object).
  • Space after //.

Long declarations, calls and chains

Braces in control flow

✅ Allowed
❌ Not allowed (Android guide)

Modifier order

Annotations first, then modifiers in this order (the IDE and ktlint fix it for you):

annotations → public / protected / private / internal → expect / actual → final / open / abstract / sealed / const → external → override → lateinit → tailrec → vararg → suspend → inner → enum / annotation / fun (as in fun interface) → companion → inline / value → infix → operator → data

Trailing commas

The official guide encourages trailing commas at declaration sites (parameters, enum entries, class properties) and leaves call sites to your discretion. They make diffs cleaner and reordering trivial. Enable in the IDE: Code Style → Kotlin → Other → Use trailing comma.

B.6Documentation comments (KDoc)

Document every public API. The official guide prefers weaving parameters into the sentence with [links] over @param/@return blocks; use the tags only when a long description doesn't fit the flow.

B.10Best practices: design & readability

Conventions make code look consistent; best practices make it work well over years. These are the habits experienced Kotlin teams apply every day.

  • Make illegal states unrepresentable. A sealed interface UiState beats three nullable fields and two Booleans.
  • Immutable data, pure functions. Data classes with val; transformations that return new values. Side effects live at the edges (repository, ViewModel).
  • Composition over inheritance. Depend on interfaces passed through constructors; reserve open/abstract for genuine “is-a” hierarchies.
  • Small, focused units. One reason to change per class; one level of abstraction per function.
  • Push nullability to the boundary. Parse/validate once (DTO → domain), then work with non-null types.
  • Prefer the standard library (buildList, groupingBy, runCatching, use, require) over hand-written equivalents.
  • Use scope functions for one purpose each — and stop at one level of nesting. A local val is often clearer.
  • Avoid premature abstraction. Duplicate twice; abstract on the third occurrence.
❌ Flags allow impossible states
✅ One state at a time

B.12Best practices: coroutines & Flow

Based on Google's Best practices for coroutines in Android and the Kotlin coroutines guide:

  1. Inject dispatchersPass CoroutineDispatcher through the constructor (default Dispatchers.IO) so tests can substitute a TestDispatcher.
  2. Suspend functions are main-safeThe function that does blocking work moves itself off the main thread with withContext; callers never have to think about threads.
  3. The ViewModel creates coroutinesUse viewModelScope for UI work; expose suspend functions and Flows from lower layers rather than launching there.
  4. Don't expose mutable typesprivate val _state = MutableStateFlow(…), val state = _state.asStateFlow().
  5. Data and business layers expose suspend functions and FlowsOne-shot calls are suspend; streams are Flow.
  6. Avoid GlobalScopeFor work that must outlive a screen, inject an application-level CoroutineScope — or use WorkManager if it must survive process death.
  7. Make coroutines cancellableLong CPU loops call ensureActive() or yield(); cleanup goes in finally.
  8. Watch out for exceptionsUncaught exceptions crash the app; catch them where you can handle them and never swallow CancellationException.
  9. Collect Flows lifecycle-awareCompose: collectAsStateWithLifecycle(); Views: repeatOnLifecycle(STARTED).
  10. Share upstream workConvert to hot state with stateIn(scope, WhileSubscribed(5_000), initial); update state atomically with update { }.
❌ Hard-coded, untestable, leaks
✅ Injected, main-safe, structured

B.14Best practices: Jetpack Compose

  • Unit-returning composables are PascalCase nouns; composables that return a value are camelCase (rememberScrollState()).
  • Every reusable composable accepts modifier: Modifier = Modifier as its first optional parameter and applies it to its root.
  • Hoist state: stateless content composables take values + callbacks; one stateful wrapper reads the ViewModel.
  • No side effects in composition: use LaunchedEffect, DisposableEffect, rememberCoroutineScope.
  • Never write state you just read during composition (backwards writes cause infinite recomposition).
  • Keys in lazy lists (items(list, key = { it.id })) and remember(key) for expensive calculations.
  • Stable, immutable parameters (data classes with val, read-only collections) let Compose skip unchanged UI.
  • Defer fast-changing reads (scroll position, animation values) into lambdas or derivedStateOf.
  • Theme tokens, not literals: MaterialTheme.colorScheme.primary, stringResource(R.string…).
  • Accessibility: contentDescription for meaningful icons, 48 dp touch targets, semantic roles.
  • Previews for each meaningful state (empty, loading, error, long text, dark theme).

B.15Best practices: performance

  • Measure first (profiler, Macrobenchmark, release builds) — optimize what the numbers show.
  • Use sequences for long chains on large collections or short-circuiting terminals; plain lists for small ones.
  • Pick the right structure: Set/Map for lookups (O(1)), not list.contains in a loop.
  • Avoid allocations in hot paths (drawing, scrolling): no lambdas creating lists per frame; reuse objects.
  • inline small higher-order functions you write for hot code; primitive arrays (IntArray) for numeric work.
  • Lazy-initialize expensive objects (by lazy, Hilt Lazy<T>, Provider<T>).
  • Ship with R8 enabled and Baseline Profiles for faster startup.

B.16Best practices: testing

  • Follow the test pyramid: many fast JVM tests, fewer device tests.
  • Fakes over mocks for your own interfaces; mocks for things you can't fake easily.
  • One behaviour per test, Arrange → Act → Assert, and a name that states the behaviour.
  • Deterministic coroutines: runTest, injected TestDispatchers, MainDispatcherRule, Turbine for Flows.
  • Test the stateless composable with plain state; test the ViewModel separately.
  • Never sleep in tests; advance virtual time instead (advanceTimeBy, advanceUntilIdle).
  • CI runs the tests and the linters on every push; a red build blocks merging.

B.17Best practices: security

🔐 Data

  • No API keys, passwords or tokens in source or BuildConfig — keep secrets on a server.
  • HTTPS only; consider certificate pinning for high-value APIs.
  • Store tokens with the Android Keystore; never in plain DataStore.
  • No personal data or tokens in logs; guard debug logging with BuildConfig.DEBUG.

🛡️ Platform

  • Components android:exported="false" unless other apps must start them.
  • PendingIntent.FLAG_IMMUTABLE by default.
  • Request the minimum permissions, at the moment they're needed.
  • Validate all external input (deep links, intents, network JSON) at the boundary.
  • Keep dependencies updated; run dependency and secret scanning in CI.

B.19Code review checklist

Correctness

  • Does it do what the ticket says, including edge cases (empty, null, max)?
  • Are errors handled where they can be handled, and nowhere swallowed?
  • Is cancellation respected; no GlobalScope, no blocking calls on main?
  • Are there tests for the new behaviour, and do they fail without the change?

Design

  • Is the code in the right layer? Does the UI contain business logic?
  • Can illegal states be represented? Could a sealed type help?
  • Is state immutable and owned by one place?
  • Smallest visibility? Any new public API documented?

Readability

  • Would a newcomer understand names without explanation?
  • Idiomatic Kotlin (B.8) rather than Java-in-Kotlin?
  • Comments explain why; no commented-out code.

Android

  • Survives rotation and process death?
  • No Context leaks; lifecycle-aware collection?
  • Strings in resources, accessibility, dark mode?
  • CI green: ktlint, detekt, tests, build?
